Date: 7 November 2026. Shop measured: local Docker PrestaShop 9.2 at `http://localhost:8080`. The live host was not modified. Demo orders were not deleted.

`live_provider_verified` is false. Do not read a green PHPUnit run as a Mangopay integration.

## Customer identity strategy

**NOT IMPLEMENTED.** This pass did not add a link column and did not create `ps_orders` from API checkout.

Current model, which must stay until a migration is written:

| Identity | Table | Order column |
| --- | --- | --- |
| API customer | `marketplace_shopper` | `marketplace_order.id_marketplace_shopper` |
| Storefront customer | `ps_customer` | `marketplace_order.id_customer` |

The two ids are not interchangeable. Copying a shopper id into `id_customer` would point at the wrong person.

Safe sequence when this is scheduled:

1. Add a nullable unique `id_customer` on `marketplace_shopper`. Do not backfill by email alone.
2. Link a row only after the person proves both accounts, or an administrator links them.
3. Keep API checkout on marketplace reservations until it uses the same stock and payment transition as the storefront gateway.
4. Only then create a native PrestaShop order from an API checkout. Do that in the marketplace module, not by editing PrestaShop core.

Until step 4, API orders and storefront orders are different records.

## Logging and retention

`entry.php` logs `marketplace api {requestId}` plus the exception message for unexpected failures. The client receives `internal_error` and not that message. Passwords, bearer tokens, and the Mangopay key are not part of that format. Audit rows are readable through the admin audit route.

Log rotation is **NOT CONFIGURED** in this repository. Production needs the host's PHP or Apache log rotation and a retention period for `marketplace_audit_log`. That table is not pruned by `runMaintenance`. Rate-limit rows older than one day are pruned. Invoice files live in the configured invoice directory with mode `0600` under a `0700` directory. Their backup is **NOT TESTED**.
